# 10. The project site is static, and the realism review is a browser draft committed as an export

Date: 2026-11-16 · Status: accepted (spec #1 story 12)

## Context

The researcher needs one place to do the realism review of the pilot corpus (spec #1 story 12) and to navigate the project: corpus, pilot checks, decisions, and later the notebook and the final report. The audience is the researcher and the teacher now, and the public at submission (spec #1 story 49 releases the synthetic corpus and results). The researcher works alone, with little time and no server to run.

## Decision

- **Static, generated by Python.** `hcai site <config> [--out site/]` writes plain HTML and CSS from the repository, with vanilla JS only where needed (review form, language switch). There is no JS framework and no build step beyond Python. Links are relative, so the site works under `https://<user>.github.io/HCAI/` and when opened from disk. Pages whose inputs are missing (corpus, results) say "not generated yet" instead of failing.
- **Variants rendered in-process.** The variant viewer and the review sample render identity variants from the frozen corpus and the name bank with the same code as `hcai variants`, but write nothing to `data/`. CI therefore needs only the committed corpus (`data/corpus/v1`, committed separately), with no API key and no API call.
- **The review record is the committed export.** Answers autosave in the browser's localStorage, which is only a draft. "Export review" downloads Markdown and JSON in the structure of `docs/pilot/cv-realism-review.md`, always in English whatever the interface language. The researcher commits these to `docs/pilot/`, and that commit is the record. The JSON records the corpus version, the sample seed and the item ids. A committed review is preloaded when there is no local draft, and a review whose corpus version or items differ is refused on preload or import, with a message. There is one reviewer: inter-rater agreement belongs to the RQ4 judge audit, not to the realism review.
- **Seeded review sample.** The review sample is chosen by a documented seeded rule: for each role, one EN CV that is not borderline (the roles take the quality levels in turn) and one PT borderline CV, covering all four origins, with genders alternating within and across roles so that each language gets both, plus every job ad in every language. The pilot's first 6-CV sample was picked by hand, so no seeded rule reproduces it exactly. As agreed, the rule and the seed win, and the first committed record is the export of this sample.
- **Hosting.** The repository is made public, so GitHub Pages works on the free plan. `.github/workflows/pages.yml` builds with uv and deploys on every push to `main`.
- **Interface language.** Interface strings come in EN and PT-PT behind a JS switch, defaulting to EN without JS. Prose from the repository (ADRs, summary, research questions) stays in English.
- **Paths.** An optional `[site]` section of the design config sets the notebook, report, results and review paths. The site links the notebook on GitHub rather than rendering it.

## Considered options

- **A server or a hosted form** (with remote storage of the answers): rejected. The review has one reviewer and is done once, and a server costs upkeep and accounts. A committed file is also reviewable and versioned like the rest of the evidence.
- **Pages from a private repository:** needs a paid plan. Deploying only once the repository is public was the alternative; the researcher chose to make it public now.
- **Reading `data/variants/`:** that directory is gitignored, so CI would have to run `hcai variants` and commit its output first.

## Consequences

- An unexported draft lives in one browser only. Clearing site data loses it, so the page asks the reviewer to export.
- Out of scope: logins, a backend or remote storage, rendering the notebook, and editing the corpus from the site.
