# 10. The project site is static, and the realism review is a browser draft committed as an export

Date: 2026-11-16 · Status: accepted (spec #1 story 12)

## Context

The researcher needs one place to do the realism review of the pilot corpus (spec #1 story 12) and to navigate the project: corpus, pilot checks, decisions, and later the notebook and the final report. The audience is the researcher and the teacher now, and the public at submission (spec #1 story 49 releases the synthetic corpus and results). The researcher works alone, with little time and no server to run.

## Decision

- **Static, generated by Python.** `hcai site <config> [--out site/]` writes plain HTML and CSS from the repository, with vanilla JS only where needed (review form, language switch). There is no JS framework and no build step beyond Python. Links are relative, so the site works under `https://<user>.github.io/HCAI/` and when opened from disk. Pages whose inputs are missing (corpus, results) say "not generated yet" instead of failing.
- **Variants rendered in-process.** The variant viewer and the review sample render identity variants from the frozen corpus and the name bank with the same code as `hcai variants`, but write nothing to `data/`. CI therefore needs only the committed corpus (`data/corpus/v1`, committed separately), with no API key and no API call.
- **The review record is the committed export.** Answers autosave in the browser's localStorage, which is only a draft. "Export review" downloads Markdown and JSON in the structure of `docs/pilot/cv-realism-review.md`, always in English whatever the interface language. The researcher commits these to `docs/pilot/`, and that commit is the record. The JSON records the corpus version, the sample seed and the item ids. A committed review is preloaded when there is no local draft, and a review whose corpus version or items differ is refused on preload or import, with a message. There is one reviewer: inter-rater agreement belongs to the RQ4 judge audit, not to the realism review.
- **Seeded review sample.** The review sample is chosen by a documented seeded rule: for each role, one EN CV that is not borderline (the roles take the quality levels in turn) and one PT borderline CV, covering all four origins, with genders alternating within and across roles so that each language gets both, plus every job ad in every language. The pilot's first 6-CV sample was picked by hand, so no seeded rule reproduces it exactly. As agreed, the rule and the seed win, and the first committed record is the export of this sample.
- **Hosting.** The repository is made public, so GitHub Pages works on the free plan. `.github/workflows/pages.yml` builds with uv and deploys on every push to `main`.
- **Interface language.** Interface strings come in EN and PT-PT behind a JS switch, defaulting to EN without JS. Prose from the repository (ADRs, summary, research questions) stays in English.
- **Paths.** An optional `[site]` section of the design config sets the notebook, report, results and review paths. The site links the notebook on GitHub rather than rendering it.

## Considered options

- **A server or a hosted form** (with remote storage of the answers): rejected. The review has one reviewer and is done once, and a server costs upkeep and accounts. A committed file is also reviewable and versioned like the rest of the evidence.
- **Pages from a private repository:** needs a paid plan. Deploying only once the repository is public was the alternative; the researcher chose to make it public now.
- **Reading `data/variants/`:** that directory is gitignored, so CI would have to run `hcai variants` and commit its output first.

## Consequences

- An unexported draft lives in one browser only. Clearing site data loses it, so the page asks the reviewer to export.
- Out of scope: logins, a backend or remote storage, rendering the notebook, and editing the corpus from the site.

### Amendment (2026-11-22): the name check is read from a committed record and drawn as static SVG (#11 Part B)

The pilot page read the name check from `results/names/`. `results/` is gitignored and the Pages workflow builds
from the committed repository, so the deployed page said "not generated yet" for a check that had been run.

- **The record is committed, like the review.** The site reads the name check from `docs/pilot/names/`
  (`[site] names`): the CSV files `hcai names` wrote, copied there and committed. That commit is the record the
  site shows. `<results>/names` is read only when that directory holds no record (no summary.csv or cells.csv
  with a row: an empty file does not stand in front of the local results), as a local preview of a run not yet
  committed; the page then says the files are local and links none of them, as it does for a `names` directory
  outside the project root. The copy is a hand step: nothing checks that the committed record is the latest run,
  and its `prompt_version`, rule parameters and re-ask limit are on the page so that a stale record can be told.
  The files must stay as `hcai names` wrote them (UTF-8, commas, decimal points). A byte order mark is dropped; a
  file that is not comma-separated (a spreadsheet's semicolon export) is refused and the page says why, since
  read as one column it would pass for a record with nothing in it.
- **Its own page.** `pilot/names.html` has the pass rule in plain words, the cell table, one chart per gender ×
  origin cell, the table of every name × model, the re-ask record and links to the CSV files on GitHub; the pilot
  page keeps the headline, the cells over all models and the link.
- **No probability or pass flag is recomputed.** Every probability and every pass mark is the CSV's own; numbers
  are only rounded to 3 decimals for display, from their decimal text. The pass flags were computed at full
  precision (ADR 0011), so a value shown at a threshold may still fail it: the mark, not the rounded number, is
  the result. What the page adds are counts of rows: the names passing, the re-asks per model, and how each
  re-asked answer ended, read from its answer on record in `perceptions.csv`.
- **Charts are inline SVG written by Python at build time** (`hcai.site_names`): no chart library, no CDN and no
  JavaScript, so they work with scripts off and from disk. Each is one image for assistive technology (named by
  its caption and `<title>`, described by its `<desc>`), with the names and models written as text, and the table
  after the charts holds every value they draw: a captioned table in a named scrolling region, each row headed
  by its name. Interface strings in them switch language like the rest; a row's hover `<title>` reads the row in
  the CSV's own words (its column names), in English.
- **Reading the origin bar.** The intended origin is always the first segment, drawn from 0 to exactly its
  share, so the rule's minimum (0.25) can be read against its end; the line is drawn only where the rule has a
  minimum (not for Portuguese names). A bar is about 130 units long, so a difference under about 0.01 cannot be
  seen: at a threshold the mark and the table say whether a row passes, and the page says so. A question with no
  estimate gets words in place of a bar and no line, since an empty bar would read as a probability of 0. Any
  two origins can touch, so the four origin colours were chosen as a set that keeps every pair apart for protan
  and deutan vision, and for normal vision, with 3:1 contrast against the page, in the light and in the dark
  theme; they are named again beside the charts of each origin. A pass or fail is a check or a cross, told apart
  by shape as well as colour. Model ids too long for their column are cut in the middle and never drawn alike.
- **Considered:** committing a rendered image (it would go stale, and has no text or theme); a JS chart library
  (a dependency and a CDN for eight small charts, and nothing without scripts); making CI run `hcai names` (it
  needs API keys and calls, which the site build must never make).

### Amendment (2026-11-22): the review page follows the reviewer, and every page reads without scripts (site UX pass)

The first review page listed its 12 items in one scroll of about 17,000 px, each checklist above its text, with no
sign of progress, and on a phone every table collapsed to one letter per line. Agreed with the researcher: one even
pass over the whole site, no deep rework.

- **"Reviewed" is derived, never recorded.** A review item counts as reviewed when every check is ticked, or when it
  has a note. The page reads this off the answers to show progress ("5 of 12 reviewed", one jump link per item).
  Nothing is stored for it: the record stays format version 1, field for field, and a saved draft loads as it is
  (same localStorage key, same shape). An unticked check with no note keeps its item "to do", so the reviewer has
  to say what does not hold.
- **The page follows the reviewer's order; the record keeps its own.** Reviewer and date, then the items, then the
  verdict and the export. Each item shows its text first, with the checklist and notes beside it on a wide screen
  (they stay in view while the text scrolls) and after it on a narrow one. The exported Markdown is unchanged, with
  the verdict first.
- **"All hold" is per item only.** One button (key `a`) ticks every check of one item. There is no page-wide one:
  the review is the evidence for freezing the corpus, so each item stays its own act.
- **Keyboard shortcuts are single keys that can be turned off.** `j` / `k` move between items, `1`–`5` tick or
  untick a check of the current item, `a` is "All hold", `n` goes to the notes, `Esc` leaves a field. They act only
  while the focus is not in a field, and a box on the page turns them off (remembered).
- **The current item is the one in view, and a key never changes anything out of sight.** The current item follows
  the scroll position; an item the reviewer is sent to (a jump link, a key, the focus) stays current until the next
  scroll, but only while it is on screen. So a page that comes back at another position (a reload, the Back button,
  an old `#item-N` in the address) cannot leave the keys acting on an item the reviewer does not see. The strip
  names the current item and how many of its checks are ticked, which is what shows a key's effect when the
  checklist itself is below the text; the same is said to a screen reader.
- **What the browser keeps** (localStorage, each optional): the draft under `hcai-review:<corpus version>:<seed>`,
  as before; `hcai-review-exported:<corpus version>:<seed>`, the answers each of the two files was last exported
  with, only to say whether they have changed since or are in one file only (it is not a record, and it is dropped
  with its draft); `hcai-review-keys` (`off`); `hcai-lang`; `hcai-theme`.
- **Theme switch.** Auto (the system's theme: the default, and what a page does without scripts), light or dark,
  remembered. One inline script in each page's `<head>` applies the choice before the first paint and marks that
  scripts run; it is the only inline script. The dark colours are written once in `style.css`, for the system
  preference, and the generator copies them under `data-theme="dark"` (`hcai.site.themed_css`).
- **Every page reads without scripts.** Scripts are deferred, so none delays the first paint. Controls that need
  them are hidden unless scripts run (`.js-only`): the two switches, the review's progress, export, import and
  shortcuts. Links, tables, the variant list and the slot highlighting of the review work without. The review form
  still needs scripts to save and export, and says so.
- **Phones.** A wide table scrolls sideways in its own box instead of squeezing its columns. The navigation is one
  row beside the site name that scrolls sideways (a menu button would need a script), with the two switches on a
  row below it, so that what is seen is in the order the keyboard reaches it. A script keeps the current and the
  focused link clear of the row's fading edge; without scripts the row still scrolls, so on a screen about 320 to
  390 px wide the last links are reached by scrolling it. The review's strip does not stick on a screen under 30rem
  high (a phone on its side, a zoomed page), where it would cover too much of the text.
- **Finding your way.** The home page is a hub: a card per part of the project, with where it stands. Deep pages
  show the pages above them and link to the previous and next base CV or decision; long pages list their sections.
  The variant viewer can put a second identity beside the first.
- **Considered:** a stepper with one item per screen (find-in-page and links to an item stop working, and it needs
  more state: a deeper rework than agreed); an explicit "reviewed" flag in the record (format version 2, with a
  migration) or in the draft only (one more click per item, and an imported review would fall back to the derived
  rule anyway); a page-wide "tick everything"; filters on the corpus index and hiding the reviewed items (9 base
  CVs per role, and the jump links already lead to what is left).
