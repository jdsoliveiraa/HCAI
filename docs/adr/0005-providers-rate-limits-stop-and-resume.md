# 5. Per-model providers; rate limits are waited out, then the run stops and resumes from the cache

Date: 2026-11-11 · Status: accepted (ticket #11, Part A); amended 2026-11-22 (request timeout, #11 Part B) 2026-11-23 (run guards, #12) and 2026-11-23 (run logs, #12)

## Context

The pilot and full run should cost nothing beyond the researcher's OpenCode Go subscription, with OpenRouter as a fallback if the subscription runs short (#11). OpenCode Go meters a usage budget over a rolling window of about 5 h (about $12). When the budget runs out the provider refuses calls until the window moves on. It reports `usage.cost = 0` on every call; what the call took from the budget is in `usage.opencode` (see *Go allowance* below, #11 Part B).

## Decision

- **Providers.** Each model is served by a named provider, an OpenAI-compatible endpoint with its own `base_url` and key variable. The built-in providers are `opencode-go` (the default) and `openrouter`. `[model_providers]` names a model's provider, so a switch is one line. The ids are each provider's own, so a switch may also mean a new id, which counts as a new model in the results.
- **The cache key holds no provider.** It is the request (model id, messages, temperature, seed, schema). The provider is a way of reaching a model id, not part of the experiment. A rerun after a switch therefore replays every call it already completed.
- **Keys** are read from the environment, filled from a gitignored `.env`. They are sent only in the Authorization header and redacted from any error text the provider echoes back. They never reach requests, responses, the cache or the results.
- **Headers.** Every call identifies as `User-Agent: hcai/<package version>`. A provider can add HTTP headers (`[providers.<name>] headers`, which cannot set Authorization or User-Agent) and a `session_header`. OpenCode Go refuses calls without `x-opencode-session` (HTTP 400 `MissingSessionID`), so the built-in `opencode-go` sends one random UUID per process, stable for the whole run. Like the key, headers are transport details: they are not part of the request, so never in the cache key, the cache, the results or the logs, and their values are masked in error text. A rerun with a new session id therefore still replays the cache. A `MissingSessionID` answer is an ordinary provider error: retried, then a missing row, and the run goes on. It is not swallowed: the first one prints a warning to stderr naming the provider (once per run), and `run_summary.json` counts them in `missing_session_errors`.
- **Rate and usage limits** (HTTP 429, or an error that names a rate or usage limit) are waited out below the cache and the call meter, so a wait counts as neither a retry nor a call. The wait is `Retry-After` if the provider sends it, else `[run] rate_limit_backoff` doubling up to `rate_limit_max_backoff`. They are not retried by the pipeline's `[run] retries`. Retried, they would turn a budget gap into `missing` rows.
- **Clean stop.** A call that would wait more than `[run] rate_limit_max_wait` seconds in all (default 6 h), or HTTP 402 (no credits), raises `ProviderExhausted`. It is a `BaseException`, so it passes the `except Exception` handlers that record agent failures as missing data. The run writes `progress.json` and no results table, and the CLI exits with code 3. Every completed call is already cached, so rerunning the same command carries on from the first call not yet made.
- **Unknown cost.** A provider that reports no price gives `cost = None`, a blank in `results.csv`. Totals sum the known prices and count `unpriced_attempts` and `unpriced_calls`. Each model in `run_summary.json` names its `provider` and `billing` (`metered` or `subscription`). The pilot also scales tokens up to the full run (`estimated_full_tokens`), which is what a subscription budget is spent on. A subscription provider's `cost = 0` without the `usage.opencode` block below is unknown too, not free.
- **Go allowance** (added in #11 Part B). An OpenCode Go answer carries `usage.opencode` with `billing_source` (`go`, or what pays instead once Extra Usage kicks in, e.g. `balance`), `allowance` (dollars taken from the Go allowance) and `list_cost`. Reading its `cost = 0` as a price made `run_summary.json` say $0 for Go runs. With the block, a call's `Usage.cost` is what it took from its billing source: `allowance` when billed to `go`, else the reported `cost` or, when that is 0, `list_cost` (our assumption: the balance is charged at list price). A call whose source is missing is recorded as `unknown`, costs its allowance and is flagged. `Usage` keeps `billing_source`, `allowance` (0 when billed elsewhere) and `list_cost`, so they reach the cache and, per row, `results.csv` (`allowance`, `billing_source`; attempts with different sources are `+`-joined). Totals add `allowance_total`/`allowance_spent`, `balance_spent`, `billing_sources` and `not_go_calls`/`not_go_attempts`; the printed summary shows the allowance per model and warns about any call not billed to `go`. The pilot adds `estimated_full_allowance`. Old cache entries and results tables load with these fields unset and add nothing to the allowance; a cost of 0 there (Go's 0 misread as a price before this change) loads as unknown, so a rerun over an old cache says "cost unknown" instead of $0. A real $0 price cached before the change (e.g. a free OpenRouter model) is therefore also unknown, the safe side. OpenCode Go has no usage or balance endpoint: the budget left is console-only, and `scripts/opencode_go_usage.py --spent` sums what a cache recorded.

### Amendment (2026-11-22): the request timeout is a `[run]` setting, default 600 s

The HTTP client waited a fixed 120 s for each answer. In the pilot run (#11 Part B), `qwen3.8-flash` as Blinder on Portuguese CVs wrote a median of 7,117 and up to 11,218 completion tokens per call, and 7 of 24 such calls ended in `ReadTimeout`. A call that raises is never cached, so every rerun asked them again and they timed out again. 29 of 1,092 pilot rows stayed `missing`: the Blinder's, then the Screener, Evaluator and Ranker rows downstream of it. These rows are not spread at random. They all fall on one model, one language and the blinding condition, which is a cell the analysis compares.

- **Setting.** `[run] request_timeout` is the seconds every provider call waits for the answer. The default is 600. It must be a number above 0 and at most 86400 (a day), and a config with any other value is refused when it loads. The upper limit is there because a number of seconds too large for the platform's clock makes every call fail at once. `configs/core.toml` sets it explicitly.
- **What it bounds.** It is the HTTP read timeout: the longest silence while the client waits for or reads the answer. A chat completion is sent whole, not streamed, so in practice it is the time the model may take to write its answer. Sending the request and waiting for a free connection get the same limit. Connecting has its own limit of 20 s (or the request timeout, if that is lower), where it shared the 120 s before. It applies to the TCP connection and again to the TLS handshake, so an unreachable provider still fails fast.
- **Scope.** One setting for every provider (`opencode-go`, `openrouter` and any `[providers.<name>]`) and every command that calls one: `hcai run`, `corpus`, `names`, `check`, and the model listings of `check` and `models`. It is not set per provider, model or agent. Which calls are slow was only visible after the pilot, and one generous limit needs no tuning.
- **No cap on the answer.** No `max_tokens` is sent and no request changes. A cap would cut the blinded CV short, which changes what the model writes and therefore the experiment. The timeout is a transport detail like the key and the headers: it is not part of the request, so it is never in the cache key or the cache. The results show it in one place only, the error text of a call that timed out. A rerun with another timeout replays every cached call and asks only the calls that never completed.
- **A call that still times out** is handled as each command already handled a failed call. It raises a provider error that names `ReadTimeout` and the setting. `hcai run` retries it (`[run] retries`) and then records its rows as `missing`. `hcai names` records a missing answer and stops after 10 failed calls in a row to one model. `hcai corpus` stops with the error. `hcai check` reports the probe as failed.

600 s is five times the old limit. It was chosen with room over the longest answer seen, not derived from a measured token rate, so the pilot rerun has to confirm it: if rows still fail with `ReadTimeout`, raise it in the config. The setting bounds only how long the client waits. Whether the provider's own gateway allows calls this long is not known, because at 120 s the client always gave up first. If the gateway cuts a call, the failure is an HTTP error (such as 504) or a dropped connection, not `ReadTimeout`, and a longer timeout does not help.

The cost is a slower failure when a provider accepts calls and never answers. In `hcai run` each agent call then takes up to (`retries` + 1) × `request_timeout`, 30 min at the defaults, before its rows are recorded as missing; it was 6 min. A run does not stop after repeated failures, so this is paid for every such call. `hcai names` stops after 10 failed calls in a row to one model, which is now up to 100 min; it was 20 min.

### Amendment (2026-11-23): run guards for the full run (#12)

The full run is about 10,000 rows over one to two days on OpenCode Go, mostly unattended. A review of the run code before it found several ways for it to spend money, lose data, or fill with `missing` rows without anyone noticing. Each guard below stops the run through `ProviderExhausted` (so `progress.json`, no results table, exit 3, and a rerun resumes from the cache) or reports what happened. None of them changes a request or a cache key. A test pins the keys of every agent's request, retry notes included, so the pilot's cache still replays.

- **Billing guard.** `[run] allowed_billing` (default `["go"]`) lists the billing sources a call may be paid from (`usage.opencode.billing_source`). The guard sits above the cache. The first fresh answer billed elsewhere is cached first, so what was paid for is kept, and then `BillingStop` stops the run. A typical case is `balance`, once Extra Usage bills the pay-as-you-go balance. The `unknown` source (an `opencode` block with no source) is not in the default list either. The stop is on the safe side, and adding `"unknown"` lets those calls through. Answers replayed from the cache were paid for by an earlier run and pass. Answers that name no billing source (OpenRouter, any other provider) are never checked. `allowed_billing = []` turns the check off. `progress.json` records `stop = "billing"` with the model and the source. `run_summary.json` lists `allowed_billing` and counts `not_allowed_billing_calls` (non-zero only when the check is off or the list was widened).
- **Consecutive failures.** Below the cache, `FailureGuard` counts failed calls in a row per model. A call that raises a `ProviderError` (including a timeout, a refused session or an empty answer) counts once. Repeating the identical request (a retry of a raised call) adds nothing, so one call that keeps failing adds 1, not 3 or 4. Only an answer from the provider resets the count, since a cache hit makes no call. At `[run] max_consecutive_failures` (default 10; 0 never stops), `TooManyFailures` stops the run with the last error (`stop = "failures"`). This replaces "a run does not stop after repeated failures" (previous amendment) and the "the run goes on" of `MissingSessionID`. An outage, a withdrawn model id or a refused session now stops the run instead of turning every later row into `missing`. *Cost:* calls fail in a fixed order and failed calls are not cached, so if ten calls in a row on one model fail for the request itself (say, a content filter), every rerun stops at the same place until the cause is fixed or the limit is raised. Through an outage, the stop comes after about ten calls of up to ~11 min each (four attempts with 630 s of waits); for calls that always time out it takes ten × 4 × `request_timeout`.
- **Transient failures.** A `ProviderError` from HTTP 5xx (also a 200 whose `error.code` is 5xx) or from a transport failure (timeout, refused or reset connection, the server's protocol error; not a local protocol or unsupported-URL error, which fails every time) is `transient`. The pipeline waits `[run] transient_backoff` seconds before each repeat (default `[30, 120, 480]`; the last value repeats) instead of `retry_backoff`. Such a call may be repeated up to `max(retries, len(transient_backoff))` times, so an outage of about 10 min is ridden out. Other raised errors keep `retry_backoff` doubling and `retries`. Malformed answers keep ADR 0002's immediate retry with a note. Only the waits and the number of repeats change, never the requests.
- **Limit words.** For HTTP status >= 400 (and an `error` in a 200 answer), the check now has three parts. An error code of 429 is a limit, in the body as well as the status. A *strong phrase* is a limit wherever it appears in the body's strings or code fields: *rate limit*, *usage limit*, *too many requests*, *quota*, *allowance*, *insufficient credits/balance/funds*, *out of/no credits*, *credits exhausted/exceeded/remaining*, *credit balance*, *subscription usage/limit*. A *weak word* (*limit*, *exceeded*, *insufficient*, *credit*, *subscription*) is a limit only in the `message` or a code field of a 4xx answer that says nothing about the request itself: no *token*, *max*, *size*, *length*, *context*, *input*, *output*, *prompt*, *payload*, *range*, *permission*, *card*, *available*, *support*, *param*, *field*, *schema* or *invalid*. Matching is case-insensitive at a word start. CamelCase and snake_case codes are split into words, so `SubscriptionUsageLimitError` contains *usage limit*. Quoted text (`'quota'`, `"credit_limit"`, but not the apostrophe of *You've*) and snake_case identifiers are dropped first, as that is where a validation error echoes the request. A 5xx answer with only weak words stays a transient server error. Status 401 still stops at once, and 402 is unchanged. *Trade-off:* a false positive (a request error taken for a limit) waits up to `rate_limit_max_wait` and stops, and so does every rerun. That is why weak words next to a request-shape word are not limits ("Input exceeds the maximum limit of 32768 tokens", "Insufficient permissions"). The reverse error is accepted: a limit worded only with weak words next to such a word, or only inside quotes, is handled as a failed call (retried, then missing), and the consecutive-failure guard stops the run if it persists.
- **Empty answers.** An answer whose content is empty or null and whose `finish_reason` is not `stop` (cut off, filtered, or no reason given) raises `ProviderError`. It is not cached, so a rerun asks again and pays again. Its usage block still reaches the meter (spend, billing sources) and the billing guard, so one billed to `balance` stops the run all the same. An empty answer the model finished (`stop`) is still an answer and follows ADR 0002. `hcai corpus` does not catch a provider error from a generator call, so an empty generation stops it with the error.
- **Timeouts.** `configs/core.toml` sets `request_timeout = 1200`. `qwen3.8-flash` as the PT Blinder can write up to about 16,000 completion tokens, past what 600 s leaves room for. `run_summary.json` counts `failed_calls` and `timed_out_calls`, overall and per model, and `progress.json` does the same for a stopped run.
- **Visibility and data safety.** After each role × language × condition × model block, one line goes to stderr: block i/N, calls, cache hits, missing rows so far, allowance and balance spent, calls per billing source, and elapsed time. `results.csv`, `review_queue.csv` and `repeats.csv` are written as soon as the calls are done, before the totals, the pilot estimate, the stability report and the proxy-leak summary, so a crash in those leaves the paid data on disk. `run_summary.json` gains `missing`: the share of missing rows among those due an answer (all but `rejected`) overall and per model × condition × language, the `target` (`[run] missing_target`, default 0.02, the #12 target) and `above_target`. The printed summary lists them, and stderr warns when the overall share is above the target. The exit code stays 0. A cache file that does not parse or is not a cache entry (zero bytes, cut short, `{}`) is deleted with a warning and counts as a miss.
- **Scope.** The billing and failure guards, the progress lines and the missing share belong to `hcai run`. `hcai names` and `hcai corpus` keep their own handling (names stops after 10 failed calls to a model; corpus stops on a provider error) and do not check the billing source.

### Amendment (2026-11-23): run logs (#12)

Until this amendment, the full run printed one stderr line per block, 36 lines in one to two days. An operator could not tell a slow call from a hung one, see a rate-limit wait coming, or say when the run would end.

- **Where.** The stdlib `logging` tree `hcai.*`, silent for a library user (a `NullHandler`) and set up by the CLI (`hcai.runlog.configure`). `hcai run` appends to `<out>/run.log` (human-readable: ISO timestamps with milliseconds and the UTC offset, level, logger) at `--log-level` (default INFO; DEBUG adds every cache hit). stderr gets INFO and up, or WARNING and up with `--quiet`. `hcai names` appends to `<out>/names.log`, while `corpus` and `check` log to stderr only. Their warnings (rate-limit waits, corrupt cache files, a refused session) were `print`s and now go through the same loggers.
- **Per call.** `hcai.pipeline.ClientLLM` opens a `runlog.Attempt` for every request it sends: one log line (INFO for an answer, WARNING for a failure or a malformed answer, ERROR for a stop, DEBUG for a cache hit) and one JSON record appended to `<out>/calls.jsonl` and flushed per line. The layers below fill in what only they see through `runlog.note`, a context variable: the cache hit and key prefix from `CachedClient`, and the HTTP status, finish reason and round-trip time from `OpenAICompatibleClient`. `RateLimitGuard` writes a `rate_limited` record of its own for each wait, with `resume_at`, and a WARNING that names the time it resumes. The run context (block, role, language, condition, CV variant or pool, repeat) comes from `RunLog`, which the runner updates as it goes. The record's `outcome` is what happened to the attempt (`ok`, `parse_error`, `timeout`, `rate_limited`, `provider_error`, `exhausted`). Whether the agent asks again is a separate field, `retry`, with `wait_s`, so a retried timeout is still visibly a timeout and not just a "retry". `latency_s` is the HTTP round trip when there was one, else the attempt's wall time.
- **Warnings and stops.** WARNING lines for every retry and its wait, every rate-limit wait, every timeout, every missing row (grouped per agent and CV or pool), a corrupt cache file, the billing guard, and each count of 5 or more failed calls in a row on one model. A stop by `ProviderExhausted` shows as the call line of the attempt that raised it (`-> exhausted`), then one `hcai.runner` ERROR line with its kind, reason and rows done. A crash is one ERROR line, with the traceback at DEBUG (the CLI already prints it, or names the error, on stderr). `progress.json` then says `crashed` (or `interrupted` after Ctrl-C), also for an error raised before the first call. A rerun first logs what ended the previous run (from its `progress.json`), then replaces the file. A missing row's warning leaves out the start of a malformed answer that its error in `results.csv` ends with. The record of the call that tripped the billing guard keeps its tokens, billing source and balance cost.
- **Heartbeat.** A daemon thread logs a heartbeat every `[run] heartbeat_s` seconds (default 300; above 0 and at most a day) and rewrites `progress.json` with status `running`, written atomically through a temporary file. The heartbeat gives the rows done of those planned and the percentage, the calls, cache hits and misses, the missing rows so far, the allowance and balance spent, rows per hour over the last interval and overall, the ETA, the current block, and what the run is doing and for how long (a call, a rate-limit wait). It runs through long silences (a 20 min timeout, a 5 h limit wait), which is when an operator most needs it. The thread reads only copies of plain counters. On exit it is stopped and joined for up to 5 s, then the run log is closed under the lock that guards `progress.json`. After that a late heartbeat writes nothing, so it cannot overwrite the stop or recreate the file a finished run deleted. Each writer uses its own temporary file. *Planned rows* are an upper bound: a judge row is counted for every C2/C3 CV, though it only follows a valid Evaluator score. They are counted as each CV or pool finishes, so the count reaches the total exactly. A stopped run's `progress.json` keeps the stop fields and adds the last progress numbers. A finished run still deletes it.
- **Start and end.** The start lines give the run id, the config path and its sha256, the git commit and whether tracked files differ from it, the corpus version, the models with their providers' base URLs and billing, the timeouts, retries, backoffs, rate-limit settings and guards, and the planned blocks, CVs, pools and rows. The end line gives rows by status, the missing share, calls, cache hits, failed and timed-out calls, and the allowance and balance spent.
- **What is never logged.** No API key, Authorization header, provider header or session id: base URLs only, and error texts come from `ProviderError`, which is already redacted, cut to 300 characters. No prompt or answer text either. A record has the prompt's length, the answer's length and a hash of it, and the cache key prefix, which finds the full text in the cache.
- **Safety.** Nothing here touches a request, so no cache key changes, and the key-pin test still passes. Every recording step swallows its own exceptions. A failure to write `calls.jsonl` (a full disk) logs one warning and drops the records, and the run goes on. A rerun gets a new run id and appends to `run.log` and `calls.jsonl`, where its replayed calls show as `cache: "hit"`. A partial last line left by a killed process is closed off before the next record. The cost is one JSON line and one log line per call, microseconds against calls of seconds to minutes. The fake full run of `configs/core.toml` (10,080 rows, 7,621 attempts: 4,801 calls and 2,820 cache hits) wrote 5.7 MB of `calls.jsonl` and 0.66 MB of `run.log` (4,881 lines). A rerun over the same cache added another 5.6 MB of records, all hits, but only 17 KB of log lines, as cache hits are DEBUG.
- **Scope.** Per-call records, the heartbeat and `progress.json` belong to `hcai run`. The other commands get the loggers and the flags.

## Consequences

A run that outlasts the subscription window either waits, unattended, or stops and resumes later with nothing repeated. A crew interrupted midway replays its earlier agents' calls from the cache. `hcai corpus` stops the same way, but writes no `progress.json`, as nothing is frozen until the end. Its unparseable generations are deliberately not cached (ADR 0002), so a resumed generation asks those again. `hcai check` probes are never cached. A refused key (HTTP 401) also stops the run, instead of filling the results with missing rows. Responses served by different providers under the same model id share cache entries. To compare providers, use a separate `--cache`.
